# 개발 로드맵

자사몰을 어떤 순서로 개발할지 정한 문서다. 각 단계는 별도 세션에서 이 문서만 읽고 시작할 수 있도록 단계별 목표·범위·결정 사항·완료 조건을 담는다.

## 목표
- 1~6단계를 마치면 "가입 → 상품 탐색 → 장바구니 → 주문 → 결제 → 주문 확인·취소"가 되는 **최소 판매 가능 제품(MVP)**이 완성된다.
- 7단계는 매출·재방문 강화 기능, 8단계는 실제 오픈을 위한 운영 준비다.

## 순서 결정 기준
1. **의존 관계**: 뒤 단계가 앞 단계의 데이터·기능을 사용한다(예: 주문은 장바구니와 회원을 사용).
2. **점진적 완성**: 각 단계가 끝날 때마다 실제로 동작하는 쇼핑몰이 한 단계씩 커진다.
3. **위험 후순위**: 돈·재고·외부 연동처럼 실수 비용이 큰 영역은 도메인 모델이 안정된 뒤에 다룬다.
4. **의존성은 필요한 단계에서 추가**: 각 단계의 "추가 예정 의존성"은 예상일 뿐이며, 실제로 사용하는 Issue에서만 추가한다.

## 진행 방식
- 단계 하나 안에서 기능 하나 = Issue 하나 = `feature/*` 브랜치 하나 = PR 하나.
- 단계를 시작할 때 "시작 전 결정할 사항"을 먼저 확정하고, 확정한 내용은 아래 [결정 기록](#결정-기록)에 남긴다.
- Issue를 마칠 때마다 [진행 현황](#진행-현황)과 결정 기록을 갱신하고, 이 갱신은 해당 작업 PR에 포함한다.
- 아래 "Issue 분할안"은 출발점이다. 단계를 시작할 때 실제 상황에 맞게 조정한다.

## 0단계. 프로젝트 기반

- **목표**: 애플리케이션이 로컬 DB에 연결된 채 기동하고, 공통 레이아웃의 첫 화면이 보이며, PR마다 CI에서 빌드·테스트가 자동으로 돈다.
- **범위**
  - 포함: Spring Boot 프로젝트 세팅, 프로필(local/test/prod)별 설정 분리, DB 연결과 Flyway 마이그레이션, Thymeleaf 공통 레이아웃, 공통 예외 처리·에러 페이지, 로깅 설정, GitHub Actions CI
  - 제외: 인증(1단계), 도메인 엔티티(각 기능 단계)
- **선행 조건**: 없음 (Gradle Wrapper 세팅 완료 상태)
- **시작 전 결정할 사항**
  - Spring Boot 버전
  - DB 종류(PostgreSQL / MySQL)
  - Lombok 사용 여부
  - 로컬 DB 실행 방식(Docker Compose 등)
- **추가 예정 의존성**: `spring-boot-starter-web`, `spring-boot-starter-thymeleaf`, `spring-boot-starter-validation`, `spring-boot-starter-data-jpa`, DB 드라이버, Flyway, `spring-boot-starter-test`, Testcontainers
- **Issue 분할안**
  1. Spring Boot 프로젝트 세팅 (빌드 스크립트, 메인 클래스, 컨텍스트 로드 테스트)
  2. DB 연결 및 Flyway 마이그레이션 기반, Testcontainers 통합 테스트 기반
  3. Thymeleaf 공통 레이아웃과 메인 화면
  4. 공통 예외 처리·에러 페이지·로깅
  5. GitHub Actions CI
- **완료 조건**
  - `./gradlew build`가 통과한다.
  - 로컬 프로필로 기동하면 메인 화면이 공통 레이아웃으로 표시된다.
  - PR을 열면 CI가 빌드·테스트를 실행한다.
  - 프로필별 설정 방법과 로컬 실행 방법이 문서화되어 있다.

## 1단계. 회원·인증

- **목표**: 고객이 회원가입·로그인·로그아웃할 수 있고, 관리자 전용 화면은 ADMIN만 접근할 수 있다.
- **범위**
  - 포함: 회원가입(입력 검증, 중복 이메일 확인), 폼 로그인/로그아웃, 비밀번호 암호화, USER/ADMIN 권한, CSRF 보호, 마이페이지 골격, 초기 관리자 계정 생성 방법
  - 제외: 소셜 로그인, 이메일 인증, 비밀번호 찾기(필요 시 7단계)
- **선행 조건**: 0단계(DB, 레이아웃, 예외 처리)
- **시작 전 결정할 사항**
  - 로그인 식별자(이메일 등)와 회원 필수 정보
  - 비밀번호 정책
  - 초기 관리자 계정 생성 방식(비밀값은 환경 변수로)
- **추가 예정 의존성**: `spring-boot-starter-security`, Thymeleaf Spring Security 연동 모듈(`thymeleaf-extras-springsecurity*`, Spring Security 버전에 맞는 것), `spring-security-test`
- **Issue 분할안**
  1. 회원 도메인과 회원가입
  2. 로그인·로그아웃과 보안 설정
  3. 권한별 접근 제어와 관리자 영역 골격
  4. 마이페이지 골격
- **완료 조건**
  - 가입한 계정으로 로그인할 수 있고, 비밀번호는 해시로만 저장된다.
  - 비로그인 사용자가 보호된 페이지에 접근하면 로그인 화면으로 이동한다.
  - USER가 관리자 URL에 접근하면 403이 반환된다.

## 2단계. 상품 카탈로그

- **목표**: 관리자가 상품을 등록·수정하고, 고객이 상품 목록·상세를 탐색·검색할 수 있다.
- **범위**
  - 포함: (관리자) 카테고리, 상품, 옵션(SKU)·가격·재고 수량, 이미지 업로드, 판매 상태(판매중/품절/숨김) / (고객) 카테고리별 목록, 상세, 키워드 검색, 정렬, 페이징
  - 제외: 리뷰·평점(7단계), 할인·쿠폰(7단계)
- **선행 조건**: 1단계(관리자 권한)
- **시작 전 결정할 사항**
  - 옵션 모델(단일 옵션 / 옵션 조합 SKU)
  - 이미지 저장소(로컬 파일로 시작하되 저장소 추상화 여부, 이후 S3 등)
  - 업로드 파일 제한(크기, 확장자)
  - 동적 검색 구현 방식(JPA Specification / QueryDSL 등)
- **추가 예정 의존성**: 결정 사항에 따라
- **Issue 분할안**
  1. 카테고리 관리
  2. 상품·옵션 등록·수정(관리자)
  3. 상품 이미지 업로드
  4. 상품 목록·상세(고객)
  5. 상품 검색·정렬·페이징
- **완료 조건**
  - 관리자가 등록한 상품이 판매 상태에 따라 고객 화면에 노출/비노출된다.
  - 허용되지 않은 파일은 업로드가 거부된다.
  - 목록 조회에 N+1 쿼리가 없다(테스트 또는 쿼리 로그로 확인).

## 3단계. 장바구니

- **목표**: 로그인한 고객이 상품 옵션을 장바구니에 담고 수량을 관리할 수 있다.
- **범위**
  - 포함: 담기, 수량 변경, 삭제, 선택 삭제, 품절·가격 변경·판매 중지 상품 표시, 재고 초과 수량 차단
  - 제외: 비회원 장바구니(필요 시 별도 Issue)
- **선행 조건**: 1단계(회원), 2단계(상품·옵션)
- **시작 전 결정할 사항**
  - 장바구니 저장 위치(DB / 세션)
  - 비회원 장바구니 지원 여부
- **추가 예정 의존성**: 없음
- **Issue 분할안**
  1. 장바구니 담기·조회
  2. 수량 변경·삭제
  3. 상품 상태 변경 반영
- **완료 조건**
  - 같은 옵션을 다시 담으면 항목이 늘지 않고 수량이 합쳐진다.
  - 재고보다 많은 수량은 담을 수 없다.
  - 다른 회원의 장바구니 항목은 수정할 수 없다.

## 4단계. 주문

- **목표**: 고객이 장바구니(또는 바로 구매)에서 주문서를 작성하고 주문을 생성할 수 있다.
- **범위**
  - 포함: 주문서(배송지, 주문 상품 확인), 주문 생성, 주문 시점 상품명·가격 스냅샷, 재고 차감과 동시성 제어, 주문 상태 모델, 주문 번호 생성
  - 제외: 실제 결제(5단계), 취소·환불(6단계)
- **선행 조건**: 3단계(장바구니)
- **시작 전 결정할 사항**
  - 주문 상태 전이(예: 결제 대기 → 결제 완료 → 배송 준비 → 배송 중 → 배송 완료 / 취소)
  - 재고 차감 시점(주문 생성 시 / 결제 완료 시)과 미결제 주문의 재고 복구 방식
  - 동시성 제어 방식(비관적 락 / 낙관적 락 / 조건부 UPDATE)
  - 배송지 관리 범위(주소록 저장 여부)
- **추가 예정 의존성**: 없음
- **Issue 분할안**
  1. 주문 도메인과 상태 모델
  2. 주문서 화면과 주문 생성
  3. 재고 차감·동시성 제어
  4. 미결제 주문 만료 처리
- **완료 조건**
  - 주문 후 상품 가격이 바뀌어도 주문 금액은 그대로다.
  - 재고 1개 상품에 동시에 여러 주문이 들어와도 1건만 성공한다(동시성 테스트로 확인).
  - 허용되지 않은 상태 전이는 예외로 막힌다.

## 5단계. 결제

- **목표**: 고객이 PG 테스트 환경에서 실제 결제 흐름으로 주문을 결제할 수 있다.
- **범위**
  - 포함: PG 결제창 연동, 서버 측 결제 승인, 결제 금액 검증, 결제 실패·이탈 처리, 결제 승인 멱등성, 웹훅 수신·검증, 결제 이력 저장, 결제 취소 API 연동
  - 제외: 부분 취소·환불 흐름 화면(6단계)
- **선행 조건**: 4단계(주문)
- **시작 전 결정할 사항**
  - PG사(예: 토스페이먼츠 등)와 결제 수단 범위
  - PG 키 관리 방식(환경 변수, 커밋 금지)
  - 결제 승인 실패·타임아웃 시 보상 처리 방식
- **추가 예정 의존성**: 원칙적으로 없음(Spring의 HTTP 클라이언트 사용). PG SDK는 필요성이 확인될 때만.
- **Issue 분할안**
  1. 결제 도메인과 PG 클라이언트
  2. 결제 요청·승인 흐름
  3. 결제 실패·이탈 처리
  4. 웹훅 수신과 상태 동기화
- **완료 조건**
  - 클라이언트가 보낸 금액이 주문 금액과 다르면 승인하지 않는다.
  - 같은 결제 승인 요청이 중복으로 와도 결제는 한 번만 처리된다.
  - PG 연동부는 외부 호출 없이 테스트할 수 있다(모의 서버 등).

## 6단계. 주문 관리

- **목표**: 고객은 주문 내역을 확인·취소하고, 관리자는 주문을 처리(배송 상태 변경, 환불)할 수 있다.
- **범위**
  - 포함: (고객) 주문 목록·상세, 주문 취소, 환불 요청 / (관리자) 주문 목록·검색, 배송 상태 변경, 송장 번호 입력, 환불 처리, 취소 시 재고 복구
  - 제외: 택배사 API 연동(필요 시 7단계 이후)
- **선행 조건**: 5단계(결제 취소)
- **시작 전 결정할 사항**
  - 고객이 직접 취소할 수 있는 상태 범위
  - 부분 취소 지원 여부
  - 주문 상태 변경 알림(메일) 포함 여부
- **추가 예정 의존성**: 알림을 포함하면 `spring-boot-starter-mail`
- **Issue 분할안**
  1. 고객 주문 내역 조회
  2. 고객 주문 취소(결제 취소·재고 복구)
  3. 관리자 주문 목록·상세
  4. 관리자 배송 상태 변경
  5. 환불 처리
- **완료 조건**
  - 취소된 주문은 결제 취소와 재고 복구가 함께 처리된다(하나라도 실패하면 일관된 상태로 남는다).
  - 고객은 자신의 주문만 조회·취소할 수 있다.

## 7단계. 부가 기능

- **목표**: 핵심 구매 흐름 위에 재구매·전환율을 높이는 기능을 추가한다.
- **범위**(각 항목이 독립 Issue 묶음이며, 우선순위는 단계 시작 시 정한다)
  - 리뷰·평점(구매 확정 고객만 작성)
  - 위시리스트
  - 쿠폰(정액/정률, 사용 조건, 중복 사용 방지)
  - 적립금
  - 주문·배송 알림 메일
  - 비밀번호 찾기·재설정
- **선행 조건**: 6단계(MVP 완성)
- **시작 전 결정할 사항**: 기능 우선순위, 할인 적용 순서(쿠폰·적립금)
- **추가 예정 의존성**: 기능별로 결정
- **완료 조건**: 기능별 Issue에서 정의

## 8단계. 운영 준비

- **목표**: 실제 서비스로 배포·운영할 수 있는 상태를 만든다.
- **범위**
  - 포함: 헬스체크·메트릭, 운영 프로필 설정, 컨테이너 이미지·배포 파이프라인, 로그 수집, 보안 점검(의존성 취약점, 보안 헤더), 성능 점검(주요 화면 쿼리)
- **선행 조건**: 6단계 이상
- **시작 전 결정할 사항**: 배포 대상 인프라, 모니터링 도구
- **추가 예정 의존성**: `spring-boot-starter-actuator`, 모니터링 도구 연동 모듈
- **완료 조건**
  - 운영 프로필로 배포한 애플리케이션의 헬스체크가 통과한다.
  - 배포 절차가 문서화되어 있고, 문서대로 재현할 수 있다.
